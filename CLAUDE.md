## Architecture

**OrbitOS (SprintStack)** is a team work management SaaS (Jira-like).

- **Frontend:** React 19 + TanStack Router (file-based) + TanStack React Query
- **SSR Framework:** TanStack Start
- **Deployment:** Vercel — `api/ssr.ts` is the serverless entry point; `vercel.json` rewrites all traffic to it
- **Local dev:** `@cloudflare/vite-plugin` / Miniflare (reads `.dev.vars`). When `VERCEL=1` is set the Cloudflare plugin is disabled automatically.
- **Database:** Neon Serverless Postgres via `drizzle-orm/neon-http` — always use the pooler endpoint in `DATABASE_URL`
- **ORM:** Drizzle ORM — schema in `src/db/schema.ts`, queries via `db` proxy in `src/db/index.ts`
- **Auth:** Google OAuth 2.0 + custom HS256 JWT stored in an httpOnly `SameSite=Lax` cookie
- **UI:** Radix UI primitives (`src/components/ui/`) + Tailwind CSS 4

## Key Patterns

### Routing

Routes live in `src/routes/`. Protected routes are under `src/routes/_authenticated/` (e.g. `_authenticated.dashboard.tsx`). TanStack Router uses file-system conventions — the underscore prefix makes `_authenticated` a layout without a URL segment.

### Server Functions

All backend logic lives in `src/server-fns/`. These are TanStack Start server functions (not edge handlers). Use `*.server.ts` naming or TanStack Start's `createServerFn` — do **not** import `server-only`.

- `src/server-fns/workspace.ts` — auth primitives: `getCurrentActor()` (validates JWT from cookie), `requireWorkspaceRole()` (RBAC check), `ensurePersonalWorkspace()` (auto-creates personal org on first login)
- `src/server-fns/functions.ts` — all CRUD: tasks, projects, timesheets, todos, links, forms

### Authentication Flow

1. Login → Google OAuth redirect → callback stores user in `profiles` table
2. JWT signed with `JWT_SECRET` (HS256) set as httpOnly cookie
3. Every server function calls `getCurrentActor()` to extract and verify the session

### Workspace Model

Every user has a **personal workspace** (auto-created). Users can also belong to **organization workspaces** via `organization_memberships`. Roles: `super_admin > admin > member`. Super admin is controlled by the `profiles.is_super_admin` DB flag — bootstrap via `SUPER_ADMIN_EMAILS` env var (comma-separated); on login, matching emails get the flag set.

### Database Proxy

`src/db/index.ts` exports a lazy Proxy so `DATABASE_URL` is only read at call time (not at module init — required for the serverless/edge environment).

## Environment Variables

| Variable                            | Where used                                                           |
| ----------------------------------- | -------------------------------------------------------------------- |
| `DATABASE_URL`                      | Neon pooler connection string (server-side)                          |
| `VITE_GOOGLE_CLIENT_ID`             | Google OAuth client ID (exposed to client)                           |
| `JWT_SECRET`                        | HS256 signing key for session tokens                                 |
| `SUPER_ADMIN_EMAILS`                | Comma-separated emails granted `is_super_admin` on login (bootstrap) |
| `FIREBASE_SERVICE_ACCOUNT_KEY`      | Firebase Admin SDK — full service account JSON, stringified          |
| `VITE_FIREBASE_API_KEY`             | Firebase client config                                               |
| `VITE_FIREBASE_AUTH_DOMAIN`         | Firebase client config                                               |
| `VITE_FIREBASE_PROJECT_ID`          | Firebase client config                                               |
| `VITE_FIREBASE_STORAGE_BUCKET`      | Firebase client config                                               |
| `VITE_FIREBASE_MESSAGING_SENDER_ID` | Firebase client config                                               |
| `VITE_FIREBASE_APP_ID`              | Firebase client config                                               |
| `VITE_FIREBASE_VAPID_KEY`           | Web push VAPID key for FCM                                           |

**Local dev:** copy `.dev.vars.example` → `.dev.vars` and fill in values. Miniflare reads this file automatically.

**Vercel production:** set all variables in the Vercel dashboard → Project Settings → Environment Variables (or `vercel env add <NAME>` via CLI). `VITE_*` vars must also be added there so Vercel inlines them at build time.

## Chat Feature

Chat is built on **Firebase Firestore** (real-time messages via `onSnapshot`) + **FCM** (push notifications). All message data lives in Firestore, not Neon.

- `src/lib/firebase.ts` — client Firestore + Messaging init
- `src/lib/firebase-admin.ts` — server-side Admin SDK (lazy singleton, reads `FIREBASE_SERVICE_ACCOUNT_KEY`)
- `src/server-fns/chat.ts` — server functions: `searchChatUsers`, `generateInviteLink`, `saveFcmToken`, `sendChatNotification`, `getOrCreateDirectConversation`, `createGroupConversation`, `getProfilesByIds`
- `src/hooks/use-conversations.ts` / `use-messages.ts` — Firestore `onSnapshot` hooks
- `src/hooks/use-fcm.ts` — registers browser FCM token after Notification permission
- `src/components/chat/` — `ChatLayout`, `ConversationList`, `MessageThread`, `MessageBubble`, `UserSearchInput`, `NewConversationDialog`, `ChatContext`
- `public/firebase-messaging-sw.js` — service worker for background push (receives config via `postMessage`)
- `public/manifest.json` — PWA manifest

**Firestore collections:** `conversations`, `conversations/{id}/messages`, `userFcmTokens`, `platformInvites`

**Workspace scoping:** personal workspace → search all `profiles`; org workspace → search `organizationMemberships` for that org only.

**Before first use:** create a Firebase project, enable Firestore + Cloud Messaging, download a service account key, get the VAPID key, and add all 8 Firebase env vars above.
